# 推荐排序原型（recommender/）

混合排序的工程实现，公式：

```
Score(u, i) = α·Sim(u, i) + β·Hotness(i) + γ·PrereqMatch(u, i)
默认 α=0.75, β=0.22, γ=0.03
```

三项都在 [0,1]，都是**真实数据**算出来的，不是占位符。

## 模块

| 文件 | 作用 |
| --- | --- |
| `stats.py` | 数据读取工具。MOOCCube 里那些 `.json` 大多是 JSON Lines，`relations/` 下的是 2 列 TSV 而非 JSON，统一在这里处理。 |
| `idmap.py` | 课程 ID 映射。原始 id 含 `:` `/`，生成图文件名时被替换成 `_`，热度/选课/概念数据用的都是原始 id，必须双向对上。 |
| `popularity.py` | 从真实观看行为算热度。 |
| `prerequisites.py` | 概念级先修依赖图 + 课程→概念映射 + 先修满足度。 |
| `profile.py` | 用户画像：已学课程向量的均值池化。 |
| `build_embeddings.py` | 把 `output/graphs/v01/*.ttl` 批量转成课程嵌入矩阵并缓存。 |
| `engine.py` | 排序引擎、冷启动处理、离线评估。 |

## 数据来源（全部来自本仓库的 MOOCCube）

| 信号 | 数据源 | 规模 |
| --- | --- | --- |
| 热度 | `additional_information/user_video_act.json` | 48,640 用户真实观看行为（1.7 GB） |
| 画像 | `relations/user-course.json` | 682,753 条选课 |
| 先修 | `relations/prerequisite-dependency.json` + `course-concept.json` | 1,027 条概念依赖 / 683 门课程有概念 |
| 语义 | `output/graphs/v01/*.ttl` + `zhwiki_20180420_300d.pkl` | 目前 20 门课程 |

**关于"B 站热度"**：原计划写的是接 B 站播放/点赞/收藏/投币，但本机没有 B 站数据。
MOOCCube 自带的真实观看行为是等价可用的替代，而且更贴合"学习者是否真的在看"：

```
hotness = 0.5·log1p(独立学习者数) + 0.2·log1p(总观看次数) + 0.3·观看完成度
```

三者各自除以自身最大值归一化。用 `log1p` 是因为热门课程动辄上万学习者，
线性归一化会把其余课程全压到 0 附近。完成度取 `min(local_watching_time/video_duration, 1)`。

全量扫描结果：**685 门课程**有观看记录，最热 13,421 学习者 / 251 万次观看，耗时 11 秒。

## 用法

```powershell
. .\setup_env.ps1

# 1. 算热度（第一次跑，之后走 rec_cache/popularity.json 缓存）
python -m recommender.popularity

# 2. 构建课程嵌入缓存（增量）
python -m recommender.build_embeddings

# 3. 推荐演示 + 离线评估
python -m recommender.engine
```

## 冷启动

用户没有任何已嵌入课程时（画像为空），`Sim` 记 0 并把 α 的权重让给 β，
退化为纯热度推荐。真实用户里这种情况很常见 —— 因为目前已嵌入课程只有 20 门。

## 离线评估（留一法）

把用户最后一门已嵌入课程留出，看能否排进 top-k。**只在已嵌入课程集合内评估**，
所以样本量取决于已跑课程数。

当前 20 门课程下的结果。两组数字来自不同工具，取池方式不同，绝对值有差异但结论一致：

`compare_scoring.py`（固定用户池，300 用户，同 seed 可复现）：

| 打分方式 | top-5 命中 | top-5 MRR |
| --- | --- | --- |
| 仅相似度 | 0.867 | 0.660 |
| 相似度 + 热度 | 0.880 | 0.600 |
| **相似+热度+先修（默认）** | **0.893** | 0.606 |
| 相似+热度+先修（门控版，已否决） | 0.647 | 0.448 |

`ablation.py`（`evaluate_offline`，300 用户）：

| 配置 | top-5 命中 | top-5 MRR | top-10 命中 |
| --- | --- | --- | --- |
| 仅相似度 (1,0,0) | 0.867 | 0.660 | 0.933 |
| 仅热度 (0,1,0) | 0.697 | 0.308 | 0.943 |
| 仅先修 (0,0,1) | 0.143 | 0.051 | 0.420 |
| 相似+热度 (.78,.22,0) | 0.883 | 0.601 | 0.970 |
| **相似+热度+先修（默认）** | **0.893** | 0.606 | 0.973 |

`python -m recommender.engine` 的默认配置输出（200 用户）：top-5 命中 0.895，
top-10 命中 0.965。

### 两个必须说明的坑

1. **候选集只有 20 门课时，抽样方差极大。** 同一 seed 但取池方式不同（是否先排序），
   同一打分的命中率能从 0.66 跳到 0.87。所以 `evaluate_offline` 里先对 eligible 排序再抽样，
   `compare_scoring.py` 也是先建固定池子。**跑完全部 583 门课之前，这些数字只能说明
   "原型能跑通、各项都参与了打分"，不能当效果结论。**

2. **先修不适合当"门控"。** 试过"用户明显缺先修就乘惩罚系数"的版本，
   在 300 用户对照实验里 top-5 从 0.893 掉到 0.647，已放弃。
   可行的替代方向是二部图约束求解（把推荐当带先修 DAG 的排序问题），而不是打分加项。

## 已知局限

* **先修信号覆盖面小**：依赖图只涉及 361 个概念，而全部课程概念有 25,201 个，
  交集仅 355 个。20 门课里 14 门能算出先修分，其余 6 门记中性分 0.5。
  `course.json` 里每门课自带的 `prerequisites` 字段是自由文本
  （218 门明确"无先修"，其余是自然语言描述），不适合硬解析，暂未使用。
* **用户画像覆盖率取决于已跑课程数**：目前 583 门课里只跑了 20 门，
  绝大多数用户学过的课程还没有向量，画像覆盖率很低。
* **热度与嵌入的课程不是一个集合**：685 门有观看记录，583 门在 `course.json` 里，
  能同时拿到热度和嵌入的课程更少。交叉覆盖已在 `build_embeddings.py` 里打印。
* MRR 与命中率在权重变化下方向不一致（加热度提升命中率但降低 MRR），
  因为热度会把"泛热门"课程顶到第一位，牺牲了 top-1 的精确性。正式调参需要更大的候选集。
